1. Design character

Cocoarynth Trace is an operational product, not a confectionery advertisement. Its interface should feel precise, warm, and trustworthy. Use the cacao and labyrinth identity as a restrained brand signal while prioritizing dense, scannable information and repeated work.

Required: Product workflows must meet WCAG 2.2 Level AA and remain usable with keyboard-only navigation, screen magnification, high zoom, and common screen readers.

  • Use Cocoa 900 or Ink 900 for text on Cream 050 and white surfaces.
  • Gold is primarily a border, divider, or large decorative accent. Do not use light gold for small text on cream or white.
  • Leaf 700 may signal confirmed or healthy states, but every status also needs text or an icon with an accessible name.
  • Use the established danger and focus tokens from the application theme. A focus ring must remain visually distinct from both brand and status colors.
  • Verify text, icon, control-boundary, chart, and focus contrast in the rendered state, including hover, disabled, selected, and error variants.

3. Typography

RoleTypefaceUse
DisplayFrauncesProduct identity and restrained page-level headings only
InterfaceSource Sans 3Navigation, forms, tables, body text, and compact headings
Code and dataIBM Plex MonoIdentifiers, code, structured examples, and fixed-width comparisons
  • Do not use display-sized type inside compact panels or cards.
  • Use at least 16 CSS pixels for ordinary application body text unless a tested dense-data context requires otherwise.
  • Do not convey hierarchy through size alone. Combine a logical heading level with weight, spacing, and placement.
  • Allow browser zoom and text reflow. Do not scale font size from viewport width.

4. Layout and information density

  • Use a predictable shell with stable navigation and a clear page title.
  • Prefer unframed sections and full-width work areas over nested cards. Cards are for repeated records, bounded tools, and dialogs.
  • Use grids, tables, and definition lists when users compare values. Preserve row and column meaning for assistive technology.
  • Set stable dimensions for toolbars, icon buttons, counters, and repeated tiles so loading and hover states do not shift the layout.
  • At 400% zoom and narrow widths, reflow into a usable reading and action order without two-dimensional scrolling except for genuinely tabular content.

5. Controls and interaction

  • Use buttons for commands and links for navigation. Prefer native controls before custom widgets.
  • Use familiar icons for common compact actions, paired with an accessible name and a tooltip where meaning is not obvious.
  • Use checkboxes or toggles for binary settings, segmented controls for a small mode choice, menus for longer option sets, and proper inputs for numeric values.
  • Give every interactive element a visible focus indicator. Focus order must follow the visual and logical order.
  • Touch and pointer targets should be at least 24 by 24 CSS pixels, with larger targets for primary and frequent actions.
  • Do not require drag, hover, color perception, or precise pointer movement as the only way to complete a task.

6. Content and accessible names

  • Use concise, specific labels such as “Download passport CSV” rather than “Click here.”
  • Keep visible labels and accessible names aligned so voice-control users can identify controls.
  • Alternative text describes the image's purpose in context, not every visible detail. Decorative images use alt="".
  • Write errors that identify the problem and a next action. Associate field errors with their input and summarize multiple errors near the form heading.
  • Use plain language for operational decisions. Preserve exact identifiers and contract names where precision matters.

7. Status, motion, and feedback

  • Pair color with text, shape, or iconography for draft, issued, superseded, warning, and failure states.
  • Announce important asynchronous results without moving keyboard focus unexpectedly.
  • Use motion only to explain change or continuity. Respect prefers-reduced-motion and avoid flashing content.
  • Loading indicators must preserve layout and communicate what is still pending. Long tasks need progress or meaningful status updates.
  • Do not let transient notifications contain the only copy of an important error or recovery instruction.

8. Data displays

  • Provide a text equivalent for chart meaning and do not rely on color alone to distinguish series.
  • Use real table headers and captions for tabular data. Keep sortable state available to assistive technology.
  • Format dates, units, and percentages consistently while preserving machine-readable source values where users must audit them.
  • When truncating a value visually, provide a reliable way to inspect and copy the complete value.
  • Empty states should say what is absent and offer the next relevant action; avoid decorative marketing copy in operational screens.

9. Validation strategy

LayerMinimum practice
AuthoringSemantic HTML, labeled controls, linting, and accessible component patterns
AutomatedComponent and browser accessibility checks, contrast checks, and regression tests
ManualKeyboard workflow, focus order, zoom/reflow, screen-reader spot checks, and error recovery
Human evaluationPeriodic expert review and feedback from people with disabilities for critical workflows

Automated tools detect only a portion of accessibility barriers. A zero-violation scan is useful evidence, not a conformance claim.

10. Definition of done

  1. The workflow is complete and understandable without a pointer.
  2. Names, roles, values, states, and errors are available to assistive technology.
  3. Text and controls retain contrast in every interactive state.
  4. The page reflows at narrow widths and high zoom without obscured content.
  5. Automated checks pass and the changed workflow receives focused manual testing.
  6. Known limitations have an owner, severity, and remediation plan.
